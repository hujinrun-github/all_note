### 关键事实沉淀（后续实现直接复用）

- **权威契约在 `backend/api/mobile-v2.openapi.yaml`（1019 行）**，比读 Go 代码可靠；契约指纹 `c602dd87b040c706edb08da6aa8a8d99281e5ab5fae95b780b231774e595474c`（`backend/api/mobile-v2.sha256`）。有 `internal/mobilev2contract/openapi_test.go` 做 SHA 守卫。
- **注意坑：OpenAPI 里的 `x-command-revision-matrix` 与实现不一致**，以实现 `internal/mobilev2command/engine.go:291-316` 为准（如 `task.publish` 需 `occurrences,schedule,task` 三个 expected 键，YAML 只写了 `task`）。
- 协议 5 端点：`GET /capabilities`、`GET /snapshot`、`GET /changes`、`POST /commands`、`GET /commands/:originDeviceClientID/:commandID/receipt`，挂在 `nativeProtected` 组（`router.go:110`），中间件 `RequiredSessionOrWatch`。
- 4 个 scope 用**连字符**：`iphone-content`、`iphone-task-core`、`iphone-occurrence-window`（滑动，-30~+91 天，必传 IANA 时区）、`watch-occurrence-window`。
- scope_generation 含当地日期，跨日必须重新快照；stable scope 传时区会 410。
- 客户端最大难点：`request_digest` = `sha256:` + SHA256(JCS(信封去掉 request_digest/forwarded_by_device_client_id))，需纯 TS 实现 RFC 8785（键按 UTF-16 码元排序、非 ASCII 原样不转义、数字按 IEEE754 规则）+ SHA-256。小程序无 Web Crypto。
- 服务端 `DisallowUnknownFields` + `UseNumber`：不能多发字段，大整数走十进制字符串。
- 幂等键 `(workspace_id, origin_device_client_id, command_id)`；换 digest 必须换 command_id 否则 422。POST /commands 是同步的，无 pending 状态，receipt 只作网络超时兜底。
- mobile-v2 无服务端冲突解决，冲突由客户端处理；协议内**没有 folder 实体**，只有 `note.folder_id`。

## 追加决策：客户端存储策略（内存副本 + KV 水位）

- 用户质疑"为什么要本地持久化，不是存远程吗" → 澄清：**服务端是唯一权威数据源**，客户端持有的只是投影副本；之所以必须有，是因为写命令的 `expected` 要求客户端提供实体当前 revision（`envelope.go:27-31`，`source:"exact"` 需 uint64 字符串值，`:265-268` 校验 ≥1），而 mobile-v2 没有任何在线查询单实体 revision 的接口（只有 snapshot/changes/commands）。绕法 `source:"from_dependency_receipt"`（`:269-272`）只能覆盖离线新建。
- 决策：实体投影**只放内存**，KV（`wx.setStorageSync`）只存同步水位（令牌、scope→cursor、scope_generation、runtime_epoch、时区，几 KB）。不做文件系统持久化。
  - 理由：小程序切后台 5 秒挂起、随时被销毁，跨会话离线价值低，不值得付文件分片那套复杂度。
  - 冷启动：有 cursor 且 generation 匹配 → 增量；否则全量快照。
  - 水位要**按页写**，不要等整个 scope 拉完，否则被杀要重头拉。
  - `store.ts` 接口保持不变，日后可无痛换成文件存储。
- 设计文档 `docs/wechat-miniprogram-design.md` 已同步更新：新增 §1.4（为什么必须有投影副本）、§4.2 改写为内存副本策略、新增 §5.5 同步中断与恢复、§6/§7 同步调整。

## S1 已完成：工程骨架 + 协议地基（已验证）

- 交付文档 `docs/wechat-miniprogram-s1.md`。小程序目录 `miniprogram/`（仓库根）。
- **关键实现坑（务必记住）**：仓库的 mobile-v2 有**两套并存排序规则**
  - 对象键 → `lessUTF16`（`jcs.go:211-224`），即 RFC 8785 的 UTF-16 码元
  - 语义集合 `entities`/`identity_mappings`/`field_paths` → `lessCodePoint`（`digest.go:144-157`），**码点**，是对 RFC 的偏离
  - 判别对：U+E000 vs U+1F600。UTF-16 序 emoji 在前，码点序 U+E000 在前
  - 另：U+E000 不是控制字符（≥0x20），JCS 原样输出，不转义成 `\ue000`
- **共享 golden 向量**：`backend/testdata/mobile-v2/miniprogram-vectors.json`（14 条），Go 侧 `internal/mobilev2contract/miniprogram_vectors_test.go` 与小程序 `miniprogram/test/vectors.test.ts` 读同一文件，任一侧漂移立刻失败。生成方式：临时 dump 测试（已删除）→ 固化 JSON。同目录还有官方 `jcs-vectors.json`（7 条，被 `jcs_test.go` 消费）。
- 小程序 lib 已实现：`sha256.ts`（纯 TS，小程序无 Web Crypto / Node crypto）、`jcs.ts`、`digest.ts`、`uuid.ts`、`time.ts`、`bignum.ts`、`contract.ts`。
- 验证命令：`cd miniprogram && npm test`（vitest，24 passed）、`npm run typecheck`（tsc strict）；`cd backend && go test ./internal/mobilev2contract/`（ok）。
- 小程序工程要点：需 `@types/wechat-miniprogram`（否则 App/Page/console 无类型）；测试用 vitest，路径用 `import.meta.url` 而非 `__dirname`；`tsconfig.json` exclude `test`。

## 小程序账号信息

- **AppID：`wx2d739a54c9d9d0ea`**，已写入 `miniprogram/project.config.json`（替换 touristappid）。
- 平台规则：AppID 与小程序**一一对应**，一个 AppID 只能发布一个小程序，上传新代码会覆盖线上版本；要多个小程序需各注册账号。开发阶段可用同一 AppID 调试（只要不上传）。跨小程序打通用户身份需 UnionID（同一微信开放平台账号下才一致；不同小程序 openid 不同）—— 这正是 `mp_sessions.unionid` 字段预留的原因。
- 仍缺：**AppSecret**（code2session 用，只能放后端环境变量，禁止进小程序代码或 git）与**后端 HTTPS 已备案域名**（微信 request 合法域名硬约束）。
- 环境隔离建议：不要为测试/正式各建一个小程序，而是同一个小程序配多套后端域名（开发版/体验版可在开发者工具关闭域名校验）。
